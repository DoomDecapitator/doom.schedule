# Player manual · the full API

中文: `docs/11-玩家手册.md`

> All commands live under the `doom.schedule` namespace. Ones marked `[macro]` must be passed arguments with `{...}`.
> To let other datapacks call them too, use the function tags: `#doom.schedule:schedule` (= `doom.schedule:schedule`),
> `#doom.schedule:cancel`, `#doom.schedule:clear`. That way, if the pack internally renames a function later, your calls don't need to change.

## 1. Time units

| Written as | Unit | Conversion |
|---|---|---|
| `t` / `tick` | game tick | 1 |
| `s` / `second` | second | 20 |
| `m` / `minute` | minute | 1200 |
| `h` / `hour` | hour | 72000 |
| `d` / `day` | Minecraft day | 1728000 |

Writing any other string raises an error and `return fail` (chat shows a red `[doom.schedule] invalid unit: xxx`); it is not silently dropped.

## 2. Scheduling a task

```
function doom.schedule:schedule {run:'say hello',time:20,unit:'t',id:'my_task'}
```

| Parameter | Type | Required | Description |
|---|---|---|---|
| `run` | string | ✅ | The command to run when due (**without a leading slash**) |
| `time` | integer | ✅ | The delay value, together with `unit` |
| `unit` | `'t'`/`'s'`/`'m'`/`'h'`/`'d'` | ✅ | Time unit (single or double quotes, either works) |
| `id` | string | ✅ | Task ID; cancel/pause/resume all look tasks up by it |

Return value: `return 1` on success; `return fail` for an invalid unit.

What gets frozen at enqueue time (and restored as-is at execution time):

| Field | Where it comes from | Purpose |
|---|---|---|
| `by` | The executor's UUID (4 ints → 32-character hex string) | `execute as <that entity>` at execution time, an O(1) lookup |
| `is_player` | `1b` if the executor is a player | Decides whether a disconnect means "move to the offline queue" or "silently drop" |
| `dim` | `@s`'s `Dimension`; with no entity, three native dimensions are probed with `if dimension` | Which dimension to execute in when due |
| `posX/posY/posZ`, `rotX/rotY` | `@s`'s position and facing at enqueue time | Restored at execution time via `positioned` + `rotated` |
| `exec_time` | `gametime + time × scale` | The due criterion (absolute game tick) |

> When scheduling from a command block / console there is no executing entity, so the position comes from the command source's own coordinates
> (1.21 `/execute` semantics); the dimension is probed with `if dimension` against the three native dimensions. Custom dimensions must be registered
> by you — see [12-配置与自定义维度](12-配置与自定义维度.md).

## 3. With retry

```
function doom.schedule:schedule_with_retry {run:'say hi',time:20,unit:'t',id:'rt',retry:3,retry_delay:5}
```

| Parameter | Description |
|---|---|
| `retry` | Extra attempts after a failed execution. `retry:3` = the first try plus up to 3 more, 4 attempts in total |
| `retry_delay` | Interval between retries (ticks). Values ≤ 0 are automatically corrected to 1 |

- Retries only happen when the command returns failure (`execute store success` gets 0).
- "Command failed" covers: the target entity is gone, `execute as` can't find the entity, or the command itself has invalid syntax / unmet conditions.
- Once the retry count is exhausted the task is dropped; it will not retry forever.

## 4. Cancelling

```
function doom.schedule:cancel_one {id:'my_task'}      # recommended: delete the first match
function doom.schedule:cancel {id:'my_task'}          # old alias, equivalent to cancel_one
function doom.schedule:cancel_all {id:'group_a'}      # delete every match
function doom.schedule:clear                          # empty every queue
```

| Command | Scan range | How many are deleted | Return value |
|---|---|---|---|
| `cancel_one` | `queue[]` → `offline[]` → `paused[]` | Only the first one | `#removed` (1 = deleted something, 0 = not found) |
| `cancel_all` | `processing[]` + `queue[]` + `offline[]` + `paused[]` | All matches | `#removed` (sum of the per-queue hit counts) |
| `clear` | All four queues | Everything | None |

- `cancel_one` does not touch this tick's `processing[]`: cancelling a task from inside its own `run` has no effect.
- `cancel_all` and `clear` do process `processing[]`.
- Scanning is done entry by entry in FIFO order and never disturbs the queue's order.

## 5. Pause and resume

```
function doom.schedule:pause {id:'my_task'}     # queue[] → paused[] (first match)
function doom.schedule:resume {id:'my_task'}    # paused[] → queue[] (first match)
```

- `paused[]` is a separate queue; `restore` (offline recovery) doesn't touch it. A pause is a real pause — players logging in and out doesn't affect it.
- Both return `#removed` (1 = something was moved, 0 = not found).
- `pause` only scans `queue[]`; it doesn't touch this tick's `processing[]`.
- A resumed task goes back to the tail of the queue and keeps its `exec_time` unchanged. If the due time has long passed during the pause, it executes immediately on the next beat after `resume`.

## 6. Quick scheduling

```
function doom.schedule:api/schedule_dynamic {run:'say hi',time:20,unit:'t',prefix:'demo'}
```

- Uses `prefix` directly as the `id`; no auto-increment, no deduplication.
- If you need unique IDs, don't use this — use `schedule` directly.

## 7. Other

| Command | Effect |
|---|---|
| `function doom.schedule:get_time` | `return run time query gametime`; the return value is the current game tick, nothing is written to storage |
| `function doom.schedule:__help__` | Prints a short usage hint to chat |
| `function doom.schedule:__load__` | Called automatically by `#minecraft:load`; running it by hand rebuilds the constant tables and prints one `[doom.schedule] loaded` line |
| `function doom.schedule:__unload__` | For cleanup |

## 8. What happens when a task comes due (the `looper_exec` dispatch table)

Once a task is due it enters `processing[]`; `internal/execute/run` first checks whether the target is online, then decides where to send it:

| `#target_online` | `#success` | Has `retry` | `is_player` | Result |
|---|---|---|---|---|
| 0 | — | — | true | Moved into `offline[]`, waiting for the player to return |
| 0 | — | — | false | Silently dropped (the entity is gone, the task is meaningless) |
| 1 | 1 | — | — | Done, dequeued |
| 1 | 0 | true | — | `retry` decremented, re-enqueued after `retry_delay` |
| 1 | 0 | false | — | Dropped |
| No `by` | 0 | true | — | Retried using the command source's coordinates |
| No `by` | 0 | false | — | Dropped |

## 9. Inspecting the queue (for troubleshooting)

```
/data get storage doom.schedule:data queue
/data get storage doom.schedule:data offline
/data get storage doom.schedule:data paused
/data get storage doom.schedule:ctx processing
```

## 10. Known limitations (an honest list)

- `cancel_one` / `pause` do not apply to this tick's `processing[]`. Cancelling or pausing a task from inside its own `run` has no effect.
  If you need that semantics, use `cancel_all` / `clear`.
- `offline[]` does not accept manual writes. It is maintained only by `looper_exec`'s offline dispatch; hand-written entries lack
  fields such as `by` / `dim` / `pos*`, and `restore` will have no way to handle them.
- A task resumed after a pause does not restart its timer (`exec_time` is frozen); if the due time has passed, it executes immediately. This is deliberate:
  what's paused is "when it executes", not "how much longer to wait".
- Tasks are traversed in full every tick (`looper_scan` walks the entire due set). With thousands of tasks this adds up to noticeable MSPT cost.
  It targets server scenarios with "tens to hundreds of scheduled tasks", not writing yourself a tick-level loop task.
- This pack does no deduplication: the same `id` scheduled twice is two tasks, and `cancel_one` only removes one of them.
