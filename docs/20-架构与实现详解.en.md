# doom.schedule, a vanilla server-side scheduler

- - [GitHub](https://github.com/DoomDecapitator/doom.schedule)

> Have you ever run into this: after a server restart every scheduled task is gone, after a player disconnects nobody runs their tasks, a failed scheduling attempt gets no retry… `/schedule`'s limitations don't stop there. doom.schedule fills all of these gaps with four queues, UUID targeting, and offline recovery — a pure datapack, zero dependencies.

### Doom_Flare

doom.schedule is a datapack scheduling framework for vanilla Minecraft servers. It depends on no mod, and provides a game-time-based task queue, execution context freezing, target offline detection with automatic recovery, and failure retry.

---

### Starting from the limits of `/schedule`

The vanilla `/schedule function` command provides the most basic deferred invocation. It's sufficient for simple machines or small-scale scenarios, but as soon as persistence, cross-dimension execution, or player-facing logic is involved, its shortcomings surface quickly:

- No persistence: after a server restart, every pending schedule is gone
- No target tracking: `/schedule` can only record a function name and cannot associate it with the player or entity at execution time
- No context: at execution time the entity may already be offline or may have changed, with no way to tell
- No cancel or pause: once issued, it cannot be revoked
- No retry: a failed execution is simply a failure

doom.schedule's goal is to fill these gaps, providing a persistent, trackable, manageable task scheduling system. It is fully self-contained in a datapack, requiring no external tools or mods.

---

### Core design

doom.schedule uses game time as its time base and organizes tasks into a first-in-first-out queue. Each task records its expected execution moment at enqueue time; the tick loop walks all due tasks and executes the ones that have come due.

```
         ┌─────────────────────┐
         │    queue[]          │
         │ [task, task, ...]   │
         └──────┬──────────────┘
                │ tick: move into processing[]
                ▼
         ┌─────────────────────┐
         │  looper_scan        │
         │  walk processing[]  │
         └──────┬──────────────┘
                │
        ┌───────┴───────────────┐
        ▼                       ▼
   exec_time reached?      not due yet
        │                   back to the tail
        ▼
  looper_exec dispatch
```

Each task's data structure looks like this:

```json
{
  "run": "say hello",
  "time": 100,
  "unit": "t",
  "id": "my_task_001",
  "exec_time": 12345,
  "by": "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx",
  "dim": "minecraft:overworld",
  "posX": 0.0, "posY": 64.0, "posZ": 0.0,
  "rotX": 0.0, "rotY": 0.0,
  "is_player": true,
  "retry": 3,
  "retry_delay": 20
}
```

`exec_time` is the target game time obtained at enqueue time by adding `time` (multiplied by unit.scale) to `get_time`. In the tick loop, `looper_scan` compares `exec_time` against the current game time and executes when due.

### The enqueue flow in detail

The execution path of the `schedule` function is the entry point for understanding the whole system. It receives `{run, time, unit, id}` as macro arguments and then walks through the following flow:

#### 1. Unit validity check

```mcfunction
$data modify storage doom.schedule:ctx _.unitEntry set from storage doom.schedule:const units[{name:'$(unit)'}]
execute unless data storage doom.schedule:ctx _.unitEntry run return fail
```

It matches the passed unit name (such as `"s"`) against the constant table `const.units`. If nothing matches, it does `return fail` outright. This lookup table is initialized in `__load__`:

```json
[
  {name:"t", scale:1},       {name:"tick", scale:1},
  {name:"s", scale:20},      {name:"second", scale:20},
  {name:"m", scale:1200},    {name:"minute", scale:1200},
  {name:"h", scale:72000},   {name:"hour", scale:72000},
  {name:"d", scale:1728000}, {name:"day", scale:1728000}
]
```

Why not an if-else chain? A storage filter is an O(1) hash lookup, and adding a new unit only requires adding one record to `const.units[]`, with no function changes needed.

#### 2. Delay calculation

```mcfunction
# extract the multiplier for the unit
execute store result score #scale doom.schedule run data get storage doom.schedule:ctx _.unitEntry.scale
# compute delay = time × scale
execute if score #scale doom.schedule matches 1.. store result score #delay doom.schedule run data get storage doom.schedule:ctx _.time
execute if score #scale doom.schedule matches 1.. run scoreboard players operation #delay doom.schedule *= #scale doom.schedule
```

`time × unit.scale` gives the delay in ticks.

#### 3. Context freezing

```mcfunction
function doom.schedule:internal/schedule/context
```

Reads `@s`'s UUID, dimension, position, and facing, storing them in `ctx._`. The UUID goes through 4 int → 16 byte → 16 hex → concatenation into a string. For the dimension, it reads the entity NBT `Dimension` first; if that fails it falls back to `execute if dimension` to detect the three native dimensions, and if that fails too it uses the `known_dimensions` function tag.

#### 4. Execution time

```mcfunction
execute store result score #time doom.schedule run function doom.schedule:get_time
scoreboard players operation #time doom.schedule += #delay doom.schedule
execute store result storage doom.schedule:ctx _.exec_time int 1 run scoreboard players get #time doom.schedule
```

`game_time + delay = exec_time`. After enqueueing, `looper_scan` compares `game_time >= exec_time` every tick to decide whether to execute.

#### 5. Passing retry parameters through

`schedule_with_retry` doesn't duplicate the enqueue logic; instead it stashes the retry parameters in `ctx.temp_retry` and then calls `schedule`:

```mcfunction
$data modify storage doom.schedule:ctx temp_retry set value {retry:$(retry),retry_delay:$(retry_delay)}
$function doom.schedule:schedule {run:'$(run)',time:$(time),unit:'$(unit)',id:'$(id)'}
```

After computing `exec_time`, `schedule` checks whether `temp_retry` exists; if so it moves it into `_.retry` / `_.retry_delay` and then deletes `temp_retry`. This is a parameter-passing pattern between macros: `schedule_with_retry` preprocesses, `schedule` consumes.

#### 6. Cleanup and enqueue

```mcfunction
function doom.schedule:internal/cleanup_temp
data modify storage doom.schedule:data queue append from storage doom.schedule:ctx _
data remove storage doom.schedule:ctx _
```

`cleanup_temp` deletes every UUID intermediate field inside `ctx._` (b0..bf, h0..hf, uuid0..uuid3), so the enqueued task carries no transient data. Then the clean task is `append`ed to `data.queue[]`, and finally `ctx._` is deleted.

### The looper_exec dispatch

`looper_exec` separates target detection from command execution into two phases; inside, `looper_exec` zeroes `#target_online` and `#success`, then handles the paths:

```mcfunction
# check whether the target is online
scoreboard players set #target_online doom.schedule 0
$execute if entity $(by) run scoreboard players set #target_online doom.schedule 1

# only run when online, and record success
$execute if score #target_online doom.schedule matches 1 store success score #success doom.schedule in $(dim) positioned $(posX) $(posY) $(posZ) rotated $(rotX) $(rotY) as $(by) at @s run $(run)
```

Dispatch decisions:

| Path | `#target_online` | `#success` | Has `retry` | `is_player` | Result |
|---|---|---|---|---|---|
| Has `by` | 0 | — | — | true | Moved into `offline[]` |
| Has `by` | 0 | — | — | false | Silently dropped |
| Has `by` | 1 | 1 | — | — | Done, dropped |
| Has `by` | 1 | 0 | true | — | `retry` decremented, re-enqueued |
| Has `by` | 1 | 0 | false | true | Moved into `offline[]` |
| Has `by` | 1 | 0 | false | false | Dropped |
| No `by` | — | 0 | true | — | Retried |
| No `by` | — | 0 | false | — | Dropped |

The no-`by` path is handled by `internal/execute/run_noentity`, executing the command only under the saved dimension/coordinates/facing, without binding an executor.

This separation resolves an ambiguity in the old version: the old version couldn't distinguish "the target is offline" from "the target is online but the command failed", and both triggered a retry or a move offline.

### The four-queue architecture

The system maintains four parallel queues, each with a different responsibility:

| Queue | Purpose | Dequeue mechanism |
|------|------|---------|
| `data.queue[]` | Tasks waiting to be scheduled (FIFO) | Moved wholesale into `processing[]` every tick |
| `ctx.processing[]` | Tasks being processed in the current tick | `looper_scan` checks each one; due → execute, not due → back to queue |
| `data.offline[]` | Tasks frozen while the player is offline | `restore` recovers at most 10 per tick |
| `data.paused[]` | Tasks manually paused by the user | Only `resume` restores them manually |

The tick loop (`tick.mcfunction`):

```mcfunction
execute if data storage doom.schedule:data queue[0] run function doom.schedule:internal/looper
scoreboard players set #restore_count doom.schedule 0
execute if data storage doom.schedule:data offline[0] run function doom.schedule:internal/restore
```

`looper` moves the whole `queue[]` into `processing[]` and empties the queue, after which `looper_scan` processes each task recursively. The purpose of this design: if a due task's execution produces a new schedule (enqueue), the current tick's queue won't grow without bound.

Each step of `looper_scan`:

```mcfunction
data modify storage doom.schedule:ctx task set from storage doom.schedule:ctx processing[0]
data remove storage doom.schedule:ctx processing[0]
execute store result score #exec_now doom.schedule run data get storage doom.schedule:ctx task.exec_time
execute if score #time_now doom.schedule >= #exec_now doom.schedule run function doom.schedule:internal/looper_exec
execute unless score #time_now doom.schedule >= #exec_now doom.schedule run data modify storage doom.schedule:data queue append from storage doom.schedule:ctx task
```

Due → `looper_exec` (execute + dispatch). Not due → put back into `queue[]`. Either way, the entry is removed from `processing[]`. When `processing[]` is empty the recursion ends, and the trailing `data remove storage doom.schedule:ctx processing` in `looper` clears the empty array.

Note the way that cleanup line is written: it is unconditional, relying on the premise that "the array must be empty by the time the recursion finishes". When the queue grows to several thousand entries, the recursion hits the per-tick total command limit first and is aborted; that line still executes, wiping out the tasks that hadn't been processed yet. So the claim that it clears an empty array only holds as long as the queue stays under about 5000 entries (see section 6 of `docs/12-配置与自定义维度.md`).

Flow between queues:

```
enqueue → queue[] ──tick──→ processing[] ──due──→ execute
                             │
                             ├── not due → queue[]
                             │
                             └── offline → offline[]
                                              │
                                        restore ──online──→ queue[]
                                              │
                                        offline → wait

pause → queue[] → paused[]
resume → paused[] → queue[]
```

### Offline recovery

If the target is offline, the task is moved to the `offline[]` queue. Every tick, the `restore` function scans `offline[]` at a rate of at most 10 entries:

```mcfunction
# doom.schedule:internal/restore — restore offline tasks every tick
data modify storage doom.schedule:ctx task set from storage doom.schedule:data offline[0]
data remove storage doom.schedule:data offline[0]
function doom.schedule:internal/restore_check with storage doom.schedule:ctx task
scoreboard players set #restore_online doom.schedule 0
execute if data storage doom.schedule:ctx task.online run scoreboard players set #restore_online doom.schedule 1
data remove storage doom.schedule:ctx task.online
execute if score #restore_online doom.schedule matches 1 run data modify storage doom.schedule:data queue append from storage doom.schedule:ctx task
execute unless score #restore_online doom.schedule matches 1 run data modify storage doom.schedule:data offline append from storage doom.schedule:ctx task
data remove storage doom.schedule:ctx task
scoreboard players add #restore_count doom.schedule 1
execute if data storage doom.schedule:data offline[0] if score #restore_count doom.schedule matches ..9 run function doom.schedule:internal/restore
```

`#restore_count` increments from 0, and `matches ..9` allows 0-9, i.e. 10 recursive calls in total.

### The retry mechanism

When a command execution fails (`#success = 0`) and the task defines `retry` and `retry_delay`, the retry flow begins:

```mcfunction
# doom.schedule:internal/retry — retry logic
execute store result score #retry doom.schedule run data get storage doom.schedule:ctx task.retry
scoreboard players remove #retry doom.schedule 1
execute if score #retry doom.schedule matches 0.. store result storage doom.schedule:ctx task.retry int 1 run scoreboard players get #retry doom.schedule
execute if score #retry doom.schedule matches 0.. run scoreboard players set #delay doom.schedule 1
execute if score #retry doom.schedule matches 0.. store result score #delay doom.schedule run data get storage doom.schedule:ctx task.retry_delay
execute if score #retry doom.schedule matches 0.. if score #delay doom.schedule matches ..0 run scoreboard players set #delay doom.schedule 1
execute if score #retry doom.schedule matches 0.. store result score #now doom.schedule run function doom.schedule:get_time
execute if score #retry doom.schedule matches 0.. run scoreboard players operation #now doom.schedule += #delay doom.schedule
execute if score #retry doom.schedule matches 0.. store result storage doom.schedule:ctx task.exec_time int 1 run scoreboard players get #now doom.schedule
execute if score #retry doom.schedule matches 0.. run data modify storage doom.schedule:data queue append from storage doom.schedule:ctx task
execute if score #retry doom.schedule matches ..-1 run tellraw @a [{"text":"[doom.schedule] Retry exhausted: ","color":"red"},{"nbt":"task.id","storage":"doom.schedule:ctx"}]
```

`retry` means the number of extra attempts (`retry:3` = try 3 more times after a failure, 4 executions in total). `retry_delay` defaults to 1, and values ≤0 are automatically corrected to 1. When exhausted, it prints a warning and drops the task.

### Context freezing

At enqueue time the execution context is frozen: the current dimension, coordinates, facing, and executor UUID. The UUID is read as 4 ints via `UUID[0..3]`, decomposed byte by byte, and looked up in the table to be concatenated into a hex string:

```mcfunction
# doom.schedule:internal/schedule/context — freeze the context
execute if entity @s store result storage doom.schedule:ctx _.uuid0 int 1 run data get entity @s UUID[0]
execute if entity @s store result storage doom.schedule:ctx _.uuid1 int 1 run data get entity @s UUID[1]
execute if entity @s store result storage doom.schedule:ctx _.uuid2 int 1 run data get entity @s UUID[2]
execute if entity @s store result storage doom.schedule:ctx _.uuid3 int 1 run data get entity @s UUID[3]
execute if entity @s[type=player] run data modify storage doom.schedule:ctx _.is_player set value 1b
execute if entity @s run function doom.schedule:internal/schedule/uuid_hex
execute if data storage doom.schedule:ctx _.b0 run function doom.schedule:internal/schedule/uuid_join with storage doom.schedule:ctx _
```

`uuid_hex` decomposes the 4 ints into 16 bytes (b0..bf), the `uuid_join` macro looks up `hex_chars[]` to get 16 hex pairs, and the `uuid_concat` macro concatenates them into a UUID string:

```mcfunction
$data modify storage doom.schedule:ctx _.by set value "$(h3)$(h2)$(h1)$(h0)-$(h7)$(h6)-$(h5)$(h4)-$(hb)$(ha)-$(h9)$(h8)$(hf)$(he)$(hd)$(hc)"
```

> Note

There is a negative-value overflow fix inside `uuid_hex`. When `#byte` is negative, besides correcting `#byte` (`add 256`) you must also correct `#temp` (`remove 1`), otherwise the subsequent division is off by one:

```mcfunction
execute if score #byte doom.schedule matches ..-1 run scoreboard players remove #temp doom.schedule 1
execute if score #byte doom.schedule matches ..-1 run scoreboard players add #byte doom.schedule 256
```

After enqueueing, all UUID intermediate fields (b0..bf, h0..hf, uuid0..uuid3) are cleaned up automatically, leaving no residue in storage.

The dimension scheme:

| Level | Detection method | Scope |
|---|---|---|
| Entity dimension | `data get entity @s Dimension` | All entities, automatically supporting any dimension |
| dim_scan | `execute if dimension` | The 3 native dimensions, used for entity-less executors |
| `known_dimensions` tag | Function tag | User-defined dimensions |

Entity scheduling automatically supports any dimension. Only command block/console scheduling needs custom dimensions registered by hand:

```mcfunction
# detect a custom dimension
execute if dimension mymod:void run data modify storage doom.schedule:ctx _.dim set value "mymod:void"
```

```json
// data/doom.schedule/tags/function/known_dimensions.json
{"values": ["your_datapack:detect_void"]}
```

### API reference

All APIs are functions and accept macro arguments. Apart from `schedule_dynamic` under `api/`, they all sit at the root level.

#### Basic scheduling

```mcfunction
function doom.schedule:schedule {run:'say hello',time:5,unit:'s',id:'hello_world'}
```

| Parameter | Type | Required | Description |
|---|---|---|---|
| `run` | string | ✅ | The command to execute |
| `time` | int | ✅ | The delay value |
| `unit` | string | ✅ | Unit: `t`/`tick`, `s`/`second`, `m`/`minute`, `h`/`hour`, `d`/`day` |
| `id` | string | ✅ | The task identifier, used for cancel/pause/resume |

An invalid unit raises an error and `return fail`.

#### With retry

```mcfunction
function doom.schedule:schedule_with_retry {run:'say hi',time:20,unit:'t',id:'rt',retry:3,retry_delay:5}
```

`retry` — the number of extra attempts (3 = up to 4 executions). `retry_delay` — the retry interval in ticks (≤0 is automatically corrected to 1).

#### Cancel

```mcfunction
function doom.schedule:cancel_one {id:'hello_world'}    # recommended
function doom.schedule:cancel_all {id:'group_a'}         # cancel all
function doom.schedule:clear                              # clear everything
```

`cancel_one` — scans in the order `queue[]` → `offline[]` → `paused[]` and deletes only the first match (excluding this tick's `processing[]`).

`cancel_all` — exact ID matching, deletes every match across `processing[]` + `queue[]` + `offline[]` + `paused[]`, returning the accumulated count.

`clear` — unconditionally empties every queue.

#### Pause and resume

```mcfunction
function doom.schedule:pause {id:'hello_world'}     # move from queue into paused
function doom.schedule:resume {id:'hello_world'}     # move from paused back into queue
```

`paused[]` is independent of `offline[]` and is not disturbed by restore. It only handles `queue[]`, excluding this tick's `processing[]`.

#### Quick scheduling

```mcfunction
function doom.schedule:api/schedule_dynamic {run:'say hi',time:20,unit:'t',prefix:'demo'}
```

Uses `prefix` directly as the `id`. If you need a unique ID, use `schedule` directly.

#### Other

```mcfunction
function doom.schedule:get_time     # return the current game time
function doom.schedule:__help__      # chat help
```

### The scan pattern

`cancel_one`, `pause`, and `resume` share one scan-and-rebuild pattern. Taking `cancel_one` as the example:

```mcfunction
# cancel_one.mcfunction (simplified)
data modify storage doom.schedule:ctx scan set from storage doom.schedule:data queue
data remove storage doom.schedule:data queue
data modify storage doom.schedule:data queue set value []
$execute if data storage doom.schedule:ctx scan[0] run function doom.schedule:internal/scan/cancel_queue {id:'$(id)'}
```

Three steps: copy the source queue into `ctx.scan[]` → empty the source queue → check entry by entry.

`scan/cancel_queue` does this for each task:

```mcfunction
data modify storage doom.schedule:ctx current set from storage doom.schedule:ctx scan[0]
data remove storage doom.schedule:ctx scan[0]
execute if score #removed doom.schedule matches 1.. run data modify ... queue append ...  # target already found, keep all remaining
$execute if score #removed doom.schedule matches 0 unless data ... current{id:'$(id)'} run data modify ... queue append ...  # not found and no match, keep
$execute if score #removed doom.schedule matches 0 if data ... current{id:'$(id)'} run scoreboard players set #removed 1  # match found, mark for removal
$execute if data ... scan[0] run function ... cancel_queue {id:'$(id)'}  # recurse
```

This pattern preserves FIFO order, at the cost of copying the whole queue, O(n).

`cancel_one` scans `queue[]` → `offline[]` → `paused[]` in turn, stopping at the first match. `pause` scans `queue[]` and moves matching tasks into `paused[]`. `resume` scans `paused[]` and moves them back into `queue[]`.

### cancel_all's exact filtering

`cancel_all` uses a completely different strategy: no scanning, just an NBT filter in one step:

```mcfunction
$execute store result score #removed_queue doom.schedule run data remove storage doom.schedule:data queue[{id:"$(id)"}]
$execute store result score #removed_offline doom.schedule run data remove storage doom.schedule:data offline[{id:"$(id)"}]
$execute store result score #removed_paused doom.schedule run data remove storage doom.schedule:data paused[{id:"$(id)"}]
$execute store result score #removed_processing doom.schedule run data remove storage doom.schedule:ctx processing[{id:"$(id)"}]
```

`data remove ... [{id:"$(id)"}]` finds every element in storage whose id matches and deletes it, and `execute store result score` captures the actual number deleted. Four queues, one line each, summed and returned. This is a textbook use of the NBT filter, fusing lookup, deletion, and counting into one step.

`clear` is even more direct: it unconditionally resets every queue to an empty array.

### Execution paths

When a task comes due, `looper_exec` splits into two execution paths depending on whether a `by` field is present:

With a target entity (`execute/run`):

```mcfunction
$execute if entity $(by) run scoreboard players set #target_online doom.schedule 1
$execute if score #target_online doom.schedule matches 1 store success score #success doom.schedule in $(dim) positioned $(posX) $(posY) $(posZ) rotated $(rotX) $(rotY) as $(by) at @s run $(run)
```

Two phases: first check whether `$(by)` is online, and execute only if it is. `store success score #success` captures whether the command succeeded or failed, providing the basis for retry dispatch.

Note that the `at @s` in `as $(by) at @s` overrides the preceding `positioned` / `rotated`. With an entity target, execution uses the entity's current position, ignoring the coordinates saved at enqueue time. The saved `posX/Y/Z` and `rotX/Y` only take effect on the entity-less path (`run_noentity`), for schedules issued from a command block or console.

Without a target entity (`execute/run_noentity`):

```mcfunction
$execute store success score #success doom.schedule in $(dim) positioned $(posX) $(posY) $(posZ) rotated $(rotX) $(rotY) at @s run $(run)
```

Executes directly under the saved dimension, coordinates, and facing, without binding `@s`. Suited to schedules issued from a command block or console.

After execution, `looper_exec` decides the dispatch from the four-way combination of `#target_online`, `#success`, `retry`, and `is_player`. This amounts to a state machine implemented in mcfunction, with four booleans determining the direction of 8 outcomes.

### Performance considerations

The core loop runs in `tick.mcfunction`:

```mcfunction
execute if data storage doom.schedule:data queue[0] run function doom.schedule:internal/looper
execute if data storage doom.schedule:data offline[0] run function doom.schedule:internal/restore
```

`looper` moves the whole `queue[]` into `processing[]`, and `looper_scan` recursively walks every due task, putting the not-yet-due ones back at the tail. All due tasks execute in a single tick rather than being polled one at a time. Offline recovery restores at most 10 per tick.

UUID temporary fields are cleaned up automatically before enqueueing, leaving no storage residue.

Queue operations (`cancel_one` / `pause` / `resume`) use the scan pattern: copy the source queue into `ctx.scan[]`, empty the source queue, check entry by entry, and decide whether to keep or move out. FIFO order is preserved, at the cost of copying the entire queue.

### mcdoc autocompletion

doom.schedule provides 3 mcdoc files supporting storage completion in the Spyglass / Misode's mcdoc plugins:

| File                          | Completion scenario                                          |
| --------------------------- | --------------------------------------------- |
| `mcdoc/doom.schedule.mcdoc` | `data modify storage doom.schedule:data ...`  |
|                             | `data modify storage doom.schedule:const ...` |
|                             | `data modify storage doom.schedule:ctx ...`   |

`doom.schedule:data` completes the task fields in `queue[]`, `offline[]`, and `paused[]` (`run`, `time`, `unit`, `id`, `exec_time`, `by`, `dim`, `posX/Y/Z`, `rotX/Y`, `is_player`, `retry`, `retry_delay`, `online`).

`doom.schedule:const` completes `units[]` (name + scale) and `hex_chars[]`.

`doom.schedule:ctx` completes runtime fields such as `task`, `processing[]`, `scan[]`, `current`, `unitEntry`, `temp_retry`.

Example usage is in `function/mcdoc.mcfunction`. After installing the mcdoc plugin, type this in a `.mcfunction` file:

```mcfunction
data modify storage doom.schedule:data queue append value {run:"say hi",time:20,unit:"t",id:"demo",exec_time:0}
```

When you type up to `{`, all the task fields are suggested automatically.

### In practice: integrating into an existing datapack

doom.schedule's typical use is to replace the `/schedule` command, especially when players need to be tracked:

```mcfunction
# instead of a scoreboard timer loop
function doom.schedule:schedule {
  run:'function your_pack:do_something',
  time:2,unit:'t',
  id:'task_$(unique_id)'
}
```

Advantages: no scoreboard loop needed, and when the player goes offline the task freezes automatically and resumes when they log back in.

### Limitations and outlook

- Task data lives in storage: it disappears after a server restart. It can be persisted to a file via `data modify`, but that's outside the scope of a datapack
- Accuracy is ±1 tick: it's judged against game time, so drift doesn't accumulate, but it is affected by execution order within a single tick
- The retry mechanism is synchronous: a retry re-enqueues within the same tick chain, without skipping the tasks ahead of it in the queue
- `cancel_one` / `pause` do not apply to this tick's `processing[]`: calling `cancel_one` from inside a task's own `run` has no effect
- `offline[]` does not accept manual writes: it is managed solely by `looper_exec`'s offline dispatch
- About 5000 entries is the queue's ceiling: each level of `looper_scan` costs a dozen-odd commands, and the total command count per tick is limited (65536 by default),
  65536 ÷ 13 ≈ 5040. Past that length, further `append`s won't go in, and the excess is dropped rather than deferred (details in section 6 of `docs/12-配置与自定义维度.md`)

Comparison with similar solutions:

| Feature | bs.schedule | D-Better-Schedule | doom.schedule |
|---|---|---|---|
| Function count | ~20 | ~60 | 36 |
| Scheduling | `/schedule` fire-once | `#tick` polling | `#tick` polling |
| UUID | score + predicate | `gu` hex → `execute as` | 4int → hex → `execute as $(by)` |
| Offline | ❌ | ✅ `offline[]` | ✅ `offline[]` + restore |
| Retry | ❌ | ✅ | ✅ `schedule_with_retry` |
| Pause | ❌ | ✅ | ✅ separate `paused[]` queue |
| External dependencies | None | The `gu` library | None |
