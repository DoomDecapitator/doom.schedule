# Configuration and custom dimensions

中文: `docs/12-配置与自定义维度.md`

This pack has no configuration file. What counts as "configuration" is either an argument passed at call time, data in storage, or a function tag.

## 1. Storage layout (complete)

| Storage | Who writes it | What's inside |
|---|---|---|
| `doom.schedule:const` | `__load__` | `units[]` (the time unit table) · `hex_chars[]` (a 256-entry hex lookup table). Read-only; don't hand-edit |
| `doom.schedule:data.queue[]` | Written by `schedule` on enqueue / drained by `looper` | Tasks waiting to be scheduled (FIFO) |
| `doom.schedule:data.offline[]` | `looper_exec` dispatch | Tasks frozen because the target is offline. Maintained only by the pack itself; don't hand-write it |
| `doom.schedule:data.paused[]` | `pause` / `resume` | Tasks paused by the user |
| `doom.schedule:ctx.processing[]` | `looper` | The pile of tasks moved out this tick to be evaluated. Cleared and rebuilt every tick; don't rely on it |
| `doom.schedule:ctx.task` / `scan` / `current` / `_` / `temp_retry` | Various functions | Runtime temporary data, deleted as soon as it's used within the same tick |

A task looks like this (one entry of `queue[]`):

```snbt
{
  run: "say hello",           // the command to run when due
  time: 100,                  // the delay value (raw input)
  unit: "s",                  // the time unit (raw input)
  id: "my_task",              // task ID
  exec_time: 128400,          // absolute game tick = gametime + time*scale at enqueue time
  by: "069a79f4-...",         // target entity UUID (entity-less tasks have no such field)
  dim: "minecraft:overworld", // dimension
  posX: 0.5, posY: 70.0, posZ: 0.5, rotX: 0.0, rotY: 0.0,
  is_player: 1b,              // 1b if it's a player
  retry: 3,                   // optional: remaining retry count
  retry_delay: 5              // optional: retry interval in ticks
}
```

The corresponding structure definition is in [`../doom.schedule/mcdoc/doom.schedule.mcdoc`](../doom.schedule/mcdoc/doom.schedule.mcdoc);
it exists for editor completion (see section 4 below).

## 2. Scoreboard

There is exactly one objective:

```
doom.schedule  (dummy)
```

Its entries are all fake players starting with `#` (they don't take real player names and don't show on the sidebar):

| Fake player | Purpose |
|---|---|
| `#256` | The constant 256, used by the `uuid_hex` conversion |
| `#suid` | Internal counter |
| `#scale` / `#delay` / `#time` | Computing `exec_time` inside `schedule` |
| `#target_online` / `#success` | `looper_exec`'s verdicts |
| `#retry` / `#now` | Computing the next `exec_time` inside `retry` |
| `#exec_now` / `#time_now` | `looper_scan`'s due check |
| `#removed` / `#removed_*` | Return values of `cancel*` / `pause` / `resume` |
| `#restore_count` / `#restore_online` | `restore`'s per-tick cap and online check |

To read a value in chat: `/scoreboard players get #removed doom.schedule`.

## 3. Registering custom dimensions

Entity scheduling needs no registration: at enqueue time the `Dimension` field of `@s` is read directly, so any dimension (including modded ones) can be remembered.

Registration is only needed when there is no executing entity (command blocks, the console, or `/execute` without `as`):
in that case the pack can only guess via `execute if dimension`, which natively recognizes only `minecraft:overworld` / `the_nether` / `the_end`.

Three steps:

1. Find the dimension ID (run this while standing in that dimension)

```
/data get entity @s Dimension
```

2. Write a detection function that writes the result into `doom.schedule:ctx._.dim`:

```mcfunction
# data/your_datapack/function/detect_void.mcfunction
execute if dimension mymod:void run data modify storage doom.schedule:ctx _.dim set value "mymod:void"
```

3. Register it in the tag: edit the datapack's

```
doom.schedule/data/doom.schedule/tags/function/known_dimensions.json
```

```json
{
  "values": [
    "your_datapack:detect_void"
  ]
}
```

This tag is empty by default (`{"values": []}`); in `dim_scan` the pack runs every function in it, in order.

> Note: this edits a file inside the datapack body. If you also want the zip in `dist/` to stay consistent, re-zip it yourself
> (the top-level directory inside the zip must be `doom.schedule/`).

## 4. Editor completion (mcdoc)

The pack ships [`mcdoc/doom.schedule.mcdoc`](../doom.schedule/mcdoc/doom.schedule.mcdoc), which declares the structures of
the three storages `doom.schedule:data`, `doom.schedule:const`, and `doom.schedule:ctx`.

- Spyglass (VS Code extension): just install it; it takes effect automatically while editing `.mcfunction` files.
- Misodee.vscode-mcdoc: likewise plug-and-play.

Once active, when you type:

```mcfunction
data modify storage doom.schedule:data queue append value {
```

the editor lists `run` / `time` / `unit` / `id` / `exec_time` / `by` / `dim` / `posX` … each field with its description.

An example function is in [`../doom.schedule/data/doom.schedule/function/mcdoc.mcfunction`](../doom.schedule/data/doom.schedule/function/mcdoc.mcfunction);
it writes out one example each for the three queues, the constants, and the runtime context. You can run `function doom.schedule:mcdoc` to see the completion hints in action.

## 5. Performance-related knobs

This pack doesn't offer switches like a "per-tick processing cap", because it was never designed for huge numbers of tasks. Only two things really affect cost:

| Location | Behavior | If you want to save cost |
|---|---|---|
| `looper` / `looper_scan` | Every tick it moves the whole queue into `processing[]`, compares `exec_time` entry by entry, and pushes the not-yet-due ones back into `queue[]` | Don't schedule thousands of "a few seconds later" tasks; if the native `/schedule` delay will do, don't put it in the queue |
| `restore` | At most 10 entries are restored from the offline queue per tick (`#restore_count` stops at 10, resuming next tick) | No need to tune; this is a deliberate peak-flattening design |

## 6. How many entries a queue can hold

The ceiling comes from the command budget. `looper_scan` processes the queue recursively, each level costs a dozen-odd commands, and the total number of commands per tick has a hard cap (vanilla `max_command_sequence_length`, 65536 by default). Divide the two:

```
65536 ÷ 13 ≈ 5040
```

On real machines, the queue stops growing at 5040 entries, after which even a single `append` won't go in. This number follows the above game rule: raise it and the number grows, lower it and it shrinks.

What happens when you exceed it: the tasks aren't queued for the next tick, they're dropped. `looper` first moves the whole queue into `processing[]` and then processes it entry by entry; when it hits the command ceiling halfway through, the recursion is aborted, the trailing cleanup line still runs, and the part that never got its turn disappears along with it — without raising an error.

So don't pile up thousands of entries in the queue. If you really need to schedule many tasks, use the native `/schedule` delay, or go in batches: run one batch, then schedule the next.

Within the queue set, only `restore` (offline recovery) has a per-tick cap (10); `looper` has none. That's determined by its positioning: it's a small scheduler, not a task queue server. For everyday use, a few hundred entries is more than enough.

The real-machine MSPT numbers, stress-test scripts, and per-round reports all live in the development repository (not public); the player-facing repository doesn't carry them.
